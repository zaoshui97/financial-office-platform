# 合规沙箱应急操作手册

> 适用版本：v2.0+（Kill Switch 三触发体系）
> 适用范围：金融企业智能办公平台全体运维 / SRE / 安全管理员

---

## 1. 紧急熔断（3 种方式，任选其一）

### 方式 1：环境变量（推荐，重启生效）

修改 `.env`：

```env
SANDBOX_KILL_SWITCH=true
```

然后重启服务：

```bash
# Docker Compose
docker compose restart backend

# 或直接进程（后台）
kill -HUP $(pgrep -f "uvicorn app.main:app")
```

**优点**：配置化，git 可追踪
**缺点**：需要重启进程（约 10-30 秒生效窗口）

---

### 方式 2：文件标记（最快，1 秒生效）

在项目根目录创建标记文件：

```bash
# Linux / macOS
echo "reason=监管紧急通知" > .sandbox_killed

# Windows PowerShell
"reason=监管紧急通知" | Out-File -Encoding utf8 .sandbox_killed
```

确认文件存在：

```bash
ls -la .sandbox_killed
# -rw-r--r-- 1 user  12 Oct  3 00:00 .sandbox_killed
```

**优点**：无需重启，秒级生效
**缺点**：文件需手动清理（进程重启后仍存在）

---

### 方式 3：API 远程操作（推荐有监控大盘场景）

```bash
curl -X POST "http://127.0.0.1:8000/api/v1/compliance/sandbox/kill-switch" \
  -H "Authorization: Bearer <SUPERUSER_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{
    "enabled": true,
    "operator": "ops-zhangwei",
    "reason": "监管紧急通知：立即暂停所有合规检测"
  }'
```

响应示例：

```json
{
  "enabled": true,
  "updated_by": "ops-zhangwei",
  "updated_at": "2026-10-03T00:00:00Z",
  "reason": "监管紧急通知：立即暂停所有合规检测"
}
```

**优点**：无需登录服务器，可接入监控告警自动化
**缺点**：需要超级管理员权限

## 2. 恢复（与熔断方式对应）

### 方式 1 恢复：删除环境变量 + 重启

```env
# .env 中删除或注释
# SANDBOX_KILL_SWITCH=true
```

重启服务即可。

### 方式 2 恢复：删除文件

```bash
# Linux / macOS
rm .sandbox_killed

# Windows PowerShell
Remove-Item .sandbox_killed
```

### 方式 3 恢复：调用 resume API

```bash
curl -X POST "http://127.0.0.1:8000/api/v1/compliance/sandbox/kill-switch/resume" \
  -H "Authorization: Bearer <SUPERUSER_TOKEN>"
```

响应：

```json
{
  "enabled": false,
  "updated_by": null,
  "updated_at": "2026-10-03T00:05:00Z",
  "reason": null
}
```

## 3. 确认当前状态

```bash
curl "http://127.0.0.1:8000/api/v1/compliance/sandbox/kill-switch" \
  -H "Authorization: Bearer <USER_TOKEN>"
```

响应：

```json
{
  "enabled": false,
  "reason": null
}
```

| enabled | 状态 |
|---------|------|
| `false` | 正常运行 |
| `true`  | 已熔断，`reason` 字段显示原因 |

## 4. 熔断后的请求表现

所有沙箱 API 请求（`POST /api/v1/compliance/sandbox/chat` 等）均返回 **HTTP 503**：

```json
{
  "error_code": "SANDBOX_KILLED",
  "message": "合规沙箱已熔断，请稍后重试",
  "fallback": "none",
  "kill_switch_reason": "file:/path/to/.sandbox_killed|监管紧急通知",
  "timestamp": "2026-10-03T00:00:00Z"
}
```

## 5. 审计留痕

### 查询被熔断拦截的事件

```sql
SELECT
  id,
  user_id,
  request_id,
  prompt_preview,
  blocked,
  block_reason,
  scenario,
  created_at
FROM compliance_audit_logs
WHERE
  JSON_EXTRACT(scenario, '$.event_type') = 'kill_switch_triggered'
ORDER BY created_at DESC
LIMIT 20;
```

### 查询所有被拒绝的请求

```sql
SELECT
  id,
  user_id,
  blocked,
  block_reason,
  risk_hits,
  created_at
FROM compliance_audit_logs
WHERE blocked = 1
ORDER BY created_at DESC
LIMIT 20;
```

## 6. 告警接入建议

推荐在监控系统中配置以下告警：

| 触发条件 | 建议动作 |
|---------|---------|
| `compliance_audit_logs` 单分钟写入 > 50 条 `blocked=1` | 发送 PagerDuty / 钉钉告警 |
| `compliance_audit_logs.scenario.event_type = kill_switch_triggered` 新增记录 | 通知安全管理员 |
| `.sandbox_killed` 文件存在 | 自动发告警（用文件监控） |
| `SANDBOX_KILL_SWITCH=true` 出现于 `.env` diff | 自动通知运维 |

## 7. 故障排查

### 熔断后仍然有请求进入

1. 检查中间件注册：`/openapi.json` → `/paths/~1api~1v1~1compliance~1sandbox-*`
2. 确认请求路径以 `/api/v1/compliance/sandbox/` 开头
3. 确认 kill_switch 单例状态：

```bash
python -c "from app.sandbox.kill_switch import kill_switch; print(kill_switch.is_active(), kill_switch.reason)"
```

### 无法恢复（kill_switch 持续 active）

可能原因：`.sandbox_killed` 文件重新被创建（定时任务 / GitOps 覆盖）。

```bash
# 检查文件是否存在
ls -la .sandbox_killed

# 检查进程内存中的缓存（5 秒内不刷新）
sleep 6
curl "http://127.0.0.1:8000/api/v1/compliance/sandbox/kill-switch"
```

---

## 8. 三种触发方式优先级

```
1. env: SANDBOX_KILL_SWITCH=true   ← 最高优先级（永久）
2. file: .sandbox_killed            ← 次高（持久，进程重启仍生效）
3. api: kill_switch.activate()      ← 动态（进程生命周期）
```

三种方式**互不影响**——关闭任意一种不代表完全恢复，必须**全部清除**才算完全恢复。
